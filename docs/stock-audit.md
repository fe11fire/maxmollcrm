# Аудит складских остатков

Дата: 2026-11-13. Исходный коммит: `51cc3a3`.
Область: Stock, OrderController, Actions/Order, FormRequest, миграции и маршруты.
Это результаты аудита; перечисленные дефекты пока не исправлены.

## Существующие бизнес-правила

- Создание активного заказа списывает товары со всех складов, а не только со склада заказа.
- Увеличение позиции списывает разницу, уменьшение и удаление возвращают её на склад заказа.
- Отмена возвращает все позиции на склад заказа, сохраняя сами позиции заказа.
- Возобновление снова списывает позиции со складов; завершение остатков не меняет.
- Допустимы переходы active -> canceled, canceled -> active, active -> completed.
- Возврат на склад заказа, а не на исходные склады, соответствует текущей реализации.
  Считать это дефектом без отдельного требования нельзя.

## Критичные дефекты

### 1. Списание не защищено от конкуренции

`app/Models/Stock.php`: subStocks читает остатки без lockForUpdate;
subStock принимает уже загруженный объект и не проверяет актуальное количество.
При остатке 10 два запроса могут прочитать 10 и списать по 6: итог -2.
При полном списании второй запрос может удалить уже отсутствующую строку и всё равно записать движение.
Наличие внешней транзакции в create/update/resume само по себе это не предотвращает.

Нужно читать и проверять актуальные остатки под блокировкой внутри транзакции;
прямой вызов subStock также должен защищать инвариант stock >= 0.
Порядок блокировок товаров и складов должен быть единым для многопозиционных заказов.

### 2. Отмена не атомарна

`app/Actions/Order/CancelAction.php`: возврат всех позиций и изменение статуса
не обёрнуты в транзакцию. Ошибка на второй позиции оставляет первый возврат в БД,
а заказ активным. Повторная отмена возвращает первую позицию повторно.
Нужна одна транзакция на возврат, историю и смену статуса.

### 3. Переходы статусов и редактирование не сериализованы

CancelAction, ResumeAction, CompleteAction и OrderController::update читают заказ
через findOrFail без блокировки. Две отмены могут дважды вернуть товары,
два возобновления — дважды списать; отмена и завершение могут оба пройти проверку active.
Параллельные изменения позиции вычисляют разницу из одного старого count.
Нужно блокировать строку заказа внутри транзакции до проверки статуса и чтения позиций
во всех перечисленных операциях. Повторный недопустимый переход должен завершаться без движений.

### 4. Нет уникальности пары товар/склад

`database/migrations/2025_03_25_183641_create_stocks_table.php`:
нет первичного/уникального ключа пары product_id, warehouse_id и ограничения stock >= 0.
В diffStocks используется first -> insert -> first: два возврата могут создать две строки.
addStock/subStock обновляют или удаляют сразу все строки пары, но пишут одно движение.
Нужны новая миграция с уникальностью пары, проверка существующих дублей перед ней
и безопасное создание отсутствующего остатка. Старые миграции уже установленной БД не переписывать.
Способ обработки уже существующих дублей и отрицательных остатков определить явно.

## Другие дефекты

- **История может не совпадать с БД.** addStock/subStock вычисляют history_stocks.stock
  из старого объекта Stock; объект после изменения не обновляется. Изменение остатка и
  создание движения не имеют собственной общей транзакции и зависят от вызывающего кода.
- **Нулевая корректировка имеет побочные эффекты.** diffStocks(item, 0) создаёт отсутствующий
  остаток и движение diff=0. При списании subStocks может также логировать нулевые строки.
- **Нет проверки аргументов модели.** Отрицательный difference у subStock увеличивает остаток,
  отрицательный у addStock уменьшает. Отрицательный count у subStocks молча пропускается.
- **Недостаточная валидация количества.** В Post/PutOrderFormRequest у items.*.count
  только gt:0, нет required/integer; дробные значения и отсутствие поля не имеют надёжного
  контракта. Для items.*.id нет distinct: повторные товары допускаются.
- **Некорректная конфигурация upsert позиций.** OrderController::create передаёт выражение
  обновления вторым аргументом upsert, хотя это uniqueBy. В order_items также нет уникальной
  пары order_id/product_id. Повторный товар создаёт несколько позиций вместо одной.
  Нужно выбрать явное правило дублей (предпочтительно отклонять запрос) и закрепить его тестами.
- **StockSeeder не согласован с fillable.** Сидер использует Stock::create с product_id
  и warehouse_id, но Stock::$fillable содержит только stock. Требуется отдельно проверить
  сидирование в изолированной БД; успешный запуск миграций не доказывает корректность сидера.
- **GET изменяет данные.** routes/api_v1.php содержит GET-маршруты cancel/resume/complete.
  Их вызов при предзагрузке ссылок или обходе может изменить заказ; планировать удаление
  с учётом совместимости API.

## Проверки в Docker

Контейнеры php/mysql/nginx/phpmyadmin запущены; MySQL image mysql:8.
`docker compose exec -T php php artisan route:list --except-vendor` успешно показал маршруты.

Проверка Stock выполнена PHP-скриптом через bootstrap Laravel в контейнере php.
Созданы отдельные товар, склад и заказ; все записи проверки откатились в finally через rollBack.
Автоинкрементные идентификаторы при откате могут оставить пропуски.

| Сценарий | Результат |
| --- | --- |
| Остаток 10, два объекта загружены до списаний, каждый subStock(..., 6, ...) | Реальный stock=-2, последнее history.stock=4 |
| Вставка второй строки той же пары товар/склад | Успешна, строк пары=2 |
| diffStocks(item, 0) при отсутствующем остатке | Создана строка stock и одно движение |

Первый сценарий детерминированно воспроизводит работу с устаревшим состоянием.
Это не нагрузочный тест с двумя независимыми соединениями; реальную конкуренцию
и ожидание блокировок нужно отдельно проверить на MySQL после исправления.

`docker compose exec -T php php artisan test`: 1 passed, 1 failed.
Unit ExampleTest проходит. Feature ExampleTest ожидает GET / -> 200,
но получает 500: Please provide a valid cache path. Корневой маршрут / не зарегистрирован,
поэтому после исправления пути шаблонный тест также требует корректного ожидания/маршрута.
Складских PHPUnit-тестов нет. phpunit.xml не задаёт отдельную тестовую БД;
перед RefreshDatabase/migrate:fresh нужно обеспечить изоляцию от рабочей БД.

6. Отдельно улучшить Docker и README с командами запуска и тестирования.

Обязательные регрессии: списание с нескольких складов; точное обнуление; нехватка
товара без частичных изменений; уменьшение/удаление позиции; возврат на отсутствующий
остаток; нулевая корректировка; rollback при ошибке записи истории и в середине отмены;
повторные/недопустимые переходы; cancel против complete/update; одновременные списания
и возвраты; история после каждой операции; required/integer/distinct для входных позиций.
Архитектуру Model/Controller/Action сохранить, отдельные репозитории и сервисные слои не нужны.
